# Service placement: edy-proxy-go vs the DCs

Decision record for the 2026-09-01 goal: *"ca, dns, dhcp services can be
backed by edy-proxy-go, unless a component is more logical to host from
these DCs; PKI templates and time synchronization to a common source."*
Every row below was implemented and verified live, not just decided.

| Service | Placement | Why |
|---|---|---|
| DNS — authoritative (`ad.edt1.lab`, `_msdcs`) | **DCs** (SAMBA_INTERNAL) | Inseparable from the directory: secure dynamic updates, SRV forest, AD replication. edy-proxy-go has **no conditional forwarding** (single global upstream), and creating an `ad.edt1.lab` zone there would *blackhole* the domain — its resolver marks a query "found" on zone-suffix match alone and never forwards the misses. |
| DNS — recursion / upstream | **edy-proxy-go** (172.16.4.1:53) | All five DCs' `dns forwarder` now points at edy (was 8.8.8.8). Applied via rolling restart — samba reads the forwarder at start; `reload-config` is not enough. Wire-proven with tcpdump: dcN → 172.16.4.1:53 → answer. Chain: clients → DC (AD zones) → edy → public upstream. |
| DHCP | **edy-proxy-go** (edy-lab segment) | The only real DHCP clients are the Win11 VMs on `virbr-edy`. edy's DHCP is deliberately single-interface (SO_BINDTODEVICE to the `serve_ip` adapter, fail-closed) and a second scope is hazardous (first-scope fallback for fresh DISCOVERs), so **no scope was added for static-edt** — those containers are static-by-design (`--ip` pins, see 20-up.sh). The edy-lab scope now hands out **DNS = 172.15.4.10 (dc1), 172.20.10.1** — the w11client AD-join prerequisite. VM→dc1 TCP 389/88/636/445 + SRV lookups verified from a netns on virbr-edy (first packets drop during ARP warm-up; that is cosmetic). Note: edy DHCP emits options 1/3/6/51/53/54 only — no option 15 (DNS suffix) or 119 (search list); joined Windows machines get the suffix from the join itself. |
| CA / PKI | **edy-proxy-go** (EDY Proxy Root CA) | Every lab container already trusts the EDY root (40-agent.sh). `42-tls-from-edy-ca.sh` replaces samba's per-DC self-signed "temporary autogenerated" TLS with EDY-issued leaves: key+CSR generated inside each DC (key never leaves), SANs carried from the CSR, signed via `POST /api/certificates` profile `machine` (ServerAuth+ClientAuth, 365d), rolling restart, then LDAPS verified **from a client container against the system trust store** with hostname verification. |
| PKI templates | **lab layer** (`pki-templates.json`) | edy's signing profiles are fixed in code (`user\|machine\|code-signing\|uefi`) with no AD-CS-style template abstraction, so templates live here: named intents (domain-controller, member-server, client-auth, code-signing) mapping to profile + key + subject + SAN policy, expanded by the issuance script. A true subordinate "AD Lab Issuing CA" is blocked today: the EDY root is `pathlen:0` (leaf-only) — rotating it with a longer path length is a controller-side change. |
| Kerberos, LDAP/GC, SYSVOL | **DCs** | The domain itself. |
| Time | **edt1 host (chrony)** | edt1 syncs **upstream to Canonical's NTS-authenticated pool** (stratum 3, `chronyc tracking`) and now **serves** 172.15.4.0/24, 172.16.4.0/24, 172.20.10.0/24, 172.30.10.0/24 (`/etc/chrony/conf.d/50-lab-serve.conf`, plus `local stratum 10 orphan` for upstream outages). Containers — including every DC and therefore the PDC emulator — share the host clock by construction; NTP service verified live from client1/rdp2/client5. VMs and physical lab machines should point at their gateway address (172.20.10.1 / 172.15.4.1). MS-SNTP *signed* time for Windows domain members is not served (needs chrony+signd on a DC) — noted as a follow-up, not a gap for the current fleet. |

Operational notes:
- Changing the DC forwarder again: edit `smb.conf` in each DC **and rolling
  `podman restart`** (see lab.env FORWARDER comment). Re-run `40-agent.sh`
  afterwards — the current containers do not restart agents on their own.
- Re-issue / verify DC TLS: `42-tls-from-edy-ca.sh` (idempotent) or
  `42-tls-from-edy-ca.sh --check`.
- `tools/dc-ca.pem` (JXplorer/ldap-web trust bundle) predates the EDY-issued
  certs; re-run `tools/install-tools.sh` cert step to refresh it — or point
  tools at the system store, which now suffices.
